## Receipt contract — IMPLEMENTED / TESTED offline

`orion.acquisition-receipt.v1` contains `history`, `responses`, `metadata`, `receiptHash`. History retains the existing immutable artifact contract. Responses preserve provider price objects and HOUR resolution; session headers, login bodies and account identifiers are excluded. The raw-payload digest means canonical JSON of retained price responses, not HTTP wire bytes or response headers. The normalized digest and each observation digest use existing canonical SHA256. The original dataset content hash is preserved separately.

Verification replays provider parsing and requires canonical equality with history candles, validates the history artifact/manifest, recomputes all metadata and checks the receipt hash. Metadata includes provider, declared Demo environment, instrument/epic, H1, requested interval, returned end-exclusive interval, collection timestamp, response class, publication delay policy, raw/normalized/dataset/observation hashes, calendar identity, complete bid/ask sides, request class and execution assumptions. Unknown outer fields fail. Rehashing a fabricated forward classification, cryptographic signature claim, transport claim, environment or collection timestamp does not bypass recomputed metadata validation.

All receipts in this version are `INJECTED_OFFLINE_FIXTURE`, `UNVERIFIED_OFFLINE_FIXTURE`, `ENGINEERING_REPLAY`. Locally rehashed fabricated data can still be made internally consistent. This verifier does **not** prove source origin. It cannot distinguish a fixture copied from elsewhere from one constructed locally. An eventual unsigned broker receipt can at most rely on authenticated HTTPS/session transport and a trusted collector; a broker-session login is not a broker cryptographic signature over prices. No v1 field activates such a trust class.

`collectOfflineReceipt` requires an explicitly supplied transport function and explicit as-of time, with no default transport. It limits requests to 100 H1 hours and reuses the real adapter's context/discovery/price methods, timeout, origin and security policies. Tests supply deterministic in-memory Responses. A supplied JavaScript function remains trusted code: this API is not a sandbox capable of proving that arbitrary injected code is offline. There is no new network CLI command or daemon.

## Candle and evidence policy

The existing adapter assumes `snapshotTimeUTC` denotes bar open. Receipt metadata spells this out as `UTC_BAR_OPEN_EXISTING_ADAPTER_ASSUMPTION`. Actual provider documentation/transport confirmation is PENDING before activation. No claim of confirmed broker semantics is made. The original snapshot strings are preserved. The interval end is open plus one hour, and collection must occur at or after end plus the configured 0–3600000 ms publication delay (default 60000). Future/incomplete candles, invalid sides, duplicate bars, interval mismatches, resolution mismatch, missing open hours and declared closure bars fail.

Source publication timestamp is unavailable: `NOT_PROVIDED_BY_SOURCE_DELAY_POLICY_ONLY`. A delay policy is not independent publication evidence. Stale and delayed fixtures retain engineering identity. Empty open windows fail coverage. Empty closed windows also fail because the reused history/manifest schema requires at least one candle; empty receipt publication is PENDING. The empty provider response has an explicit rejection fixture.

## Journal bridge and identity — PARTIAL / appendable accounts BLOCKED

`appendReceiptObservations` verifies a receipt, requires identical declared calendars, publishes an immutable content-addressed receipt sidecar, and appends existing journal-v1 observations as `ENGINEERING_REPLAY`. `sourceRevision` binds the receipt hash. A crash can leave a harmless published sidecar before any observations; retry resumes through existing candle idempotence. A correction creates a quarantined revision. Old observation files are never overwritten. Multiple chunks are separately committed, so the whole receipt import is not an all-or-nothing transaction. Existing journal locking serializes each batch.

Journal inspection verifies observation history, not the continued existence of receipt sidecars. The standalone receipt verifier verifies the receipt. No source-authentication upgrade or new financial cursor semantics are implied. Existing duplicate handling preserves the first provenance classification and receipt reference; a later receipt for identical content does not promote it.

F2 cannot currently support appendable datasets safely. Its full dataset binding is intertwined with pending intents, configuration identity, financial event identity and recovery. A v2 mode would require a stable run/genesis identity, independently committed source-prefix extension records, full prefix validation, and source cursor plus financial checkpoint in the same account transaction. It must retain original declarations and event IDs for legacy sessions and demonstrate unchanged reference financial effects. That migration is NOT IMPLEMENTED. Dataset verification was not disabled or rewritten. Tests explicitly prove source growth leaves all four fixed account identities and prior financial snapshots intact, with one pending record. This is evidence of a preserved safety boundary, not successful appendable execution.
